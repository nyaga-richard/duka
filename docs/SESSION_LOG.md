## Continuation: the four things a shopper could not do

The chosen track was "more storefront features", and the four candidates turned out to share one cause: the shop assumed the browser still held the session that placed the order. A guest who closed the tab, switched phones or cleared cookies had no way back to their order; the delivery options were a literal array in `cart/page.tsx`; the hold was a timestamp the shopper had to interpret; and stock that moved after "add to cart" surfaced only as a line of small print. This round fixes all four, on the storefront and the two API surfaces they need.

**Order lookup by number.** There was no way to read an order without the cookie it was placed with — `GET /orders/:orderId` is ownership-scoped, which is right, but it left a guest with no recovery path at all. `POST /api/v1/orders/lookup` now takes `{order_number, email}` and returns the same `getOrderView` shape the owned route returns. It is public, so it can be the _only_ unauthenticated read of an order; it is therefore narrow on purpose: both halves must match, `upper()`/`lower()` compare so a pasted number or an odd-cased address still works, a miss returns one fixed `404 "No order matches that number and email address"` so neither half can be probed, the body is `.strict()` so extra fields are `422`, and `rateLimit(db, "order-lookup:<ip>", 10, 900)` runs before the query. `/orders` is the new page: recent orders for whoever this browser still holds, and beside it the lookup form; a hit renders the full order through the same component the owned page uses.

**Delivery options, actually from the store.** `cart/page.tsx` carried `SHIPPING = [300, 500, 0]` — a copy of three `shipping_method` rows that `placeOrder` already re-reads and re-prices server-side, so the client copy could only ever drift. `GET /api/v1/catalog/shipping-methods` (public, active rows only, ordered by id) is now the source: the select shows the real name, fee and estimate, the delivery stat card and the total follow the selected option, and the fallback array in the page is labelled as a fallback that cannot misprice an order. The `min_days`/`max_days`/`code` columns the seed always had are now used, so "Nairobi standard delivery — KES 300 · 1–2 days" is generated rather than typed.

**Stock warnings that block.** `item.available` was already returned by `/cart`; the page showed "Only N in stock" and left the button live. Now a line that lost stock between adding and checking out says _Sold out — remove this line to continue_ or _Only N left — reduce the quantity_, a red banner above the total names every short line with its real availability, and **Place order** is disabled until the cart is honest again. Cheap-to-collide cases (`available === quantity`) still warn in amber instead of pretending to be an error.

**Saved address and repeat order.** No schema change: the checkout remembers the last address typed on that device (`localStorage.duka:last-address`) and offers it filled in, with a _Clear saved address_ action in the card heading; it stays on the device rather than becoming a server-side address book the API does not have. Repeat order is `ReorderButton` on any order view: it adds each line back through the existing `POST /cart/items`, caps the quantity at the 20 the API accepts, reports the lines the store can no longer fill instead of aborting the basket, and only navigates to the cart when something landed.

Also in this round: the live hold countdown (`HoldTimer`) replaces the static "stock is held until 14:32:07" line and refreshes the cart when the window closes; the order view was extracted to `components/OrderDetail.tsx` so `/orders/[orderId]` and the lookup result cannot drift apart; shipments (carrier, tracking number/link, status) are shown on the order page now that the view returns them; the success panel names the order number and says where to find it again; and `SiteNav` gained **Orders**.

Verified here: `npm run typecheck` clean; `npm run build:web` clean with one new static route (`/orders`, `/admin` and `/cart` still static, `/orders/[orderId]` and `/p/[slug]` dynamic); `npm test` **93/93** including the new `tests/integration/order-lookup.test.ts` (delivery options public + deactivation hides them; lookup from a client with no cookie and no CSRF token; case/whitespace tolerance; wrong-email, wrong-number and unknown-number all identical `404`s; strict-body `422`s; the rate limit actually closing). A live pass on PGlite (`/tmp/duka-ui5`, API :4100 behind `next start` :3100) placed a guest order for the Linen Table Runner with the countrywide courier and then read it back three ways: `POST /orders/lookup` on :4100 with no cookies (`EC-20261117-00001`, `placed`/`pending`, `Countrywide courier`, shipping `500.00`, total `2350.00`, one line carrying `variant_id: 2` so reorder can work), the same call with the number lower-cased and padded (`200`), and a wrong email (`404` with the fixed message). Through the storefront proxy, `POST /api/v1/orders/lookup` and `GET /api/v1/catalog/shipping-methods` both answer from :3100, `/`, `/orders`, `/cart`, `/admin`, `/orders/1` and `/p/linen-table-runner` all render `200`, and the compiled client chunks contain `catalog/shipping-methods`, `orders/lookup`, `duka:last-address`, the stock banner copy and the reorder label — the browser bundle really is the new one. ## Continuation: an account, a front page, and a desk that can actually stock the shop

Four asks, one gap underneath them: the storefront had no customer identity at all (only the API did), the front page _was_ the catalogue, and the desk could publish a product it had no way to create, price or stock. So this round is a landing page, a real account area, and the catalogue administration the desk was missing.

**Customers can register and sign in.** `/account/register`, `/account/login` and `/account` exist now, and the topbar carries an **Account** entry that reads the session and follows `auth:changed`, so it flips between "Sign in" and "Hi, Amina" without a reload. The account page shows the profile, the customer's order history (each row linking to the order), a password change (`POST /auth/change-password`, which revokes other sessions) and sign out. The cart page nudges guests toward an account at checkout and after the order is placed, and `/orders` stays the no-account fallback.

The part that made this more than three forms: a guest cart used to be stranded the moment someone registered, because `cart` belongs to exactly one owner (`ck_cart_owner`) and the new customer's cart starts empty. `adoptGuestCart` re-points the guest's cart row to the customer instead of copying lines — reservations hang off `cart_id`, so the 15-minute holds survive with it — and only when the customer has no active cart of their own; an empty guest cart is left to expire. Login and register both report `cart_adopted`, and the browser drops the now-meaningless guest cookie.

**A landing page with featured products.** `/` is now a front page: hero with the promise and two calls to action, the search box, a small facts row, the featured products, category tiles, a "Recently added" band and the three promises (live stock, holds, findable orders). The catalogue moved to `/shop` intact — same hero, filter strip, chip bar, sort, pagination, streamed grid — with `SearchBar`, `SortSelect` and `CatalogueGrid` taking a `basePath`, and `/?q=…`, `/?category=…`, `/?sort=…` now `307` to `/shop` with the filters preserved so old links keep working. Featured products come from `GET /catalog/products?featured=true`, which already existed and had no way to be set; when nothing is featured the page says so and shows the newest products instead, and a shop with no published products still shows one honest card pointing at the desk.

**The desk can create products and set variants.** `POST /admin/products`, `GET|PATCH /admin/products/:productId`, `POST /admin/products/:productId/variants` and `PATCH /admin/variants/:variantId` (all `catalog.write`) back a new `ProductSheet` in the catalogue tab: name, summary, description, publish state, category, brand and the feature flag, then a variant table where each SKU's price, stock on hand, compare-at price and option values are editable, with publish/unpublish per variant. The old promise in the empty state — "create products locally" — was not true before this round; it is now. Variant options are created on demand (`product_option`/`product_option_value`), a price or compare-at mismatch is `422`, a duplicate SKU or slug is `409`, and a product with no active variant cannot be published at all — which is what stops an empty product appearing on the shop.

## Continuation: the shop, dressed like Apple, wearing the ERP's photos

Two asks that turned out to be one: "consider https://www.apple.com/ for UI inspiration" and "should also use the images from ERP if available". The second one had no path at all — the shop had no public image URL and the pull threw the ERP's attachment id away — so it had to be built before it could be dressed.

**Where the image gap actually was.** The ERP already returns `image_attachment_id` on every product (`GET /api/v1/products`, first `attachments` row with `entity='product'` and `mime_type LIKE 'image/%'`, in `apps/api/src/services/catalog.ts`), and the adapter's `ErpProduct` type already had the field. What was missing: `pullCatalog` never wrote it to `product_image`, and the only read path was `GET /api/v1/attachments/:id` — permission-checked, session-bound, and pointed at a host the browser must never reach. So the shop could not show an ERP photo even if it had known which one.

**Copy nothing, proxy on demand.** `packages/erp-adapter` gained `listProductAttachments()` and `downloadAttachment()` (typed `ErpAttachment`/`ErpBinary`), `HttpErpTransport` gained `download()` — no retries, one re-login on `401`, typed timeout/unavailable errors — and the fake ERP now serves `/products/:id/attachments` and `/attachments/:id` with real bytes plus an `attachImage()` helper, so the protocol can be proven in tests. The contract file lists both as verified capabilities (`catalog.product_images`, `catalog.attachment_download`). On the shop side, `pullCatalog` records the ERP attachment as `/api/v1/catalog/images/<attachmentId>` in `product_image` — the shop's own URL, never the ERP's — and replaces that row when the ERP's photo changes, while leaving an operator's own `https` image alone. `GET /api/v1/catalog/images/:attachmentId` (public) then fetches the bytes through the adapter and streams them with `cache-control: public, max-age=600`, behind a 64-entry ten-minute cache. It is deliberately narrow: the attachment id must appear on a **published** product's image row, so it cannot be used as a general ERP file downloader, and a malformed id or path traversal is a plain `404`. If the ERP is unreachable the route answers a 1×1 transparent PNG with `no-store` — a tile loses its photo, never shows a broken-image icon, and nothing wrong is cached. `endpoint()` grew a `raw` response so this one route can send bytes while still being registered (and therefore documented) like every other route. Operators also got `PUT /admin/products/:productId/image` to set, replace or clear a product's primary image, accepting an absolute `https` URL or a path this site serves, and refusing `javascript:`, `data:` and protocol-relative URLs because the value ends up in an `img src`.

**The look.** `apps/web/app/storefront.css` is a new, deliberately narrow skin: white page, `#f5f5f7` panels, hairlines instead of borders, one system blue (`#0071e3`) for links and the primary action, a 48px translucent blurred nav (wordmark, centred 12px links, actions right), pill buttons, and display type that carries the page — 17px body, 21px lede, 40–72px headlines with tight tracking. Every selector is scoped to `.shop-layout`, so the store desk at `/admin` keeps the ERP design system untouched and nothing about routing, data or server actions changed. The landing page was recomposed along apple.com's lines: a centred statement with the search box, a stage-sized hero product on a pale panel, a two-up tile row, a quiet four-up shelf, a category strip, and a pale band of small print — with the stage choosing a product that _has_ a photo so the marquee is never a monogram, and the shelf never repeating what is already above it. `/shop` keeps its filters but reads them as one segmented control; the product page puts a sticky square gallery beside a single-plane buy column (options, details, specs separated by hairlines, one pill button per option row); cart, checkout, auth and the footer followed. Photos are letterboxed (`object-fit: contain`) rather than cropped, because catalogue shots are not lifestyle crops.

Also here: `npm run demo:catalogue` (opt-in, idempotent, not shipped data in the seed) publishes six products from `apps/web/public/seed` — one deliberately without a photo, so the monogram fallback is visible on the front page — plus a staff account and a shopper account; `docs/API.md` regenerated (**58 endpoints**); `docs/TESTING.md` (**112 tests**) and the ERP connection guide gained the photo flow.

Verified here: `npm run typecheck` clean; `npm run build` and `npm run build:web` clean; `npm test` **112/112**, including the new `tests/integration/product-images.test.ts` (attachment listing, real PNG round-trip, unsupported-transport error, pull writes the proxy URL and replaces it when the ERP's photo changes, the route serves bytes with a long cache header, `404`s for unknown/malformed/traversal/unpublished, the transparent-pixel degrade with `no-store`) and an extended `admin-catalog.test.ts` (set, replace, clear an image; `javascript:`, `data:` and `//host` refused; a site-relative path accepted). ## Continuation: two repositories instead of one directory

The e-commerce service had grown into a full application — its own API, worker, storefront, migrations, adapter package, 112 tests and a deployment overlay — living in `ecommerce/` inside this monorepo, which meant the ERP's CI, release zip, `npm ci` and the shop's were in each other's way. It is now its own repository, **`nyaga-richard/duka-ecommerce`**, with the history that touched `ecommerce/` carried across (19 commits, replayed by `git filter-branch --subdirectory-filter`; nothing was squashed or re-authored), and the ERP repo no longer contains a line of shop code.

**What moved.** The code moved as-is (the split is a path rewrite, not a rewrite of the application): the shop's `apps/api`, `apps/web`, `packages/shared`, `packages/erp-adapter`, `database/`, `docker/`, `docs/`, `scripts/` and `tests/` are the repository root there. The deployment overlay moved with it — `deploy/ecommerce/{compose.shop.yml,shop.sh,init-shop-env.sh,README.md}` became `deploy/` in the shop repo, because the thing that knows how to build and run the shop should live next to the shop.

**What had to be re-wired.** The overlay was written assuming it lived _inside_ the ERP checkout: `compose.shop.yml` used `context: ../../ecommerce` and relied on Compose resolving the same relative path against either compose file's directory, and `shop.sh` derived the ERP root as `$(dirname $0)/../..`. Neither survives a split. So: the shop repo's `deploy/shop.sh` now finds the ERP at `../duka` or `$ERP_DIR`, and names its own checkout to Compose as `$SHOP_REPO_DIR` (Compose resolves a relative build context against the first compose file's project directory, so the shop's source has to be spelled out). `init-shop-env.sh` reads the ERP host default from `$ERP_DIR/deploy/docker/.env.production` and writes `SHOP_REPO_DIR` into `.env.shop`. On the ERP side, `go-live.sh` and `update.sh` keep driving the same Compose project but now locate the shop's overlay, `.env.shop`, backup key and `shop.sh` in `../duka-ecommerce` (or `$SHOP_REPO_DIR`), refuse with a clear message when that checkout is absent rather than half-provisioning, and pass `SHOP_REPO_DIR` into every Compose invocation. Services, networks, volumes, hostnames, health gates and the backup/rollback logic are unchanged.

**Housekeeping.** The shop repo gained a CI workflow (typecheck, tests, format check), `.gitignore` entries for its operator state (`deploy/.env.shop`, `deploy/secrets/`, `deploy/backups/`), a README section explaining the two-repository layout, and a prettier pass across the whole tree so the format gate is green from its first commit. In this repo: `ecommerce/` and `deploy/ecommerce/` are gone, `docs/DEPLOYMENT.md` documents the sibling checkout, the Caddyfile comments and `self-check.sh` remedies name the shop repo's `deploy/shop.sh`, and the root README points at the new repository.

**Verified.** In a scratch checkout of the split: `npm ci`, `npm run typecheck`, `npm run build`, `npm run build:web`, `npm run format:check` and `npm test` **112/112** — none of it referencing the ERP's source, which is the point of the split. In this repo: `bash -n` on `go-live.sh`, `update.sh`, `self-check.sh`, `init-shop-env.sh` and `shop.sh`; a repo-wide grep shows no remaining reference to the removed paths except the deliberate ones (the shop database is still named `ecommerce`, and `update.sh` keeps its rsync excludes so an older host's `deploy/ecommerce/` is not damaged by a release that no longer contains it). **Not verified:** Docker was not available, so no `docker compose config`, image build, container boot or upgrade path was executed — the overlay's behaviour is argued from its files, exactly as it was before the split, and host acceptance is still required.

The split history and its content are prepared locally; pushing them needs the empty repository to exist first.
