`shop.sh diag` on the live host settled the storefront 404 in one pass, and the answer was in the adapted config, not in the mount:

```
[{"host":["shop.trustedsystems.co.ke","path","/api/*","/health/*"]}] -> subroute
      (no matcher: catch-all) -> reverse_proxy shop-api:4100
```

One `host` matcher holding **four** values: a named-matcher line takes a single matcher, so `@shop_api host {$SHOP_PUBLIC_HOST} path /api/* /health/*` had swallowed `path` and its arguments as extra hostnames. The route therefore matched **every** path on the storefront hostname — `/`, `/cart`, `/api/v1/health/live` — and the shop API answered them all with its JSON `NOT_FOUND`, while `/api/v1/catalog/products` looked healthy and the ERP host (single-matcher line) was never affected. That also explains the two dead ends: `--force-recreate` could not help (the bytes were already correct) and `caddy adapt` "listed both upstreams" because both routes existed, one with a broken matcher. The hash mismatch `diag` reported was real but benign: the mounted file was the committed `ab77331` version, i.e. simply older than the just-merged PR.

Fixed by putting each matcher on its own line inside a block, in `deploy/cloudflare/Caddyfile` (the direct-TLS file never had two matchers on a line). Two guards so it cannot ship silently again: `diag` now inspects the compiled matcher sets and prints `MALFORMED MATCHER: 'host' contains matcher name(s) path` when a matcher name appears as another matcher's *value*, and `shop.sh up`/`proxy` assert the behaviour rather than the syntax — the loopback origin must answer `<SHOP_PUBLIC_HOST>/` with `200 text/html`, otherwise the command names the API-answered case and exits non-zero (it skips politely when no loopback `:8080` listener exists, i.e. direct-TLS mode).
